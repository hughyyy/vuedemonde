# Release rendering script (planned — NOT implemented)

Status: **planned only.** This document records the requirement so it can be
implemented after the 0.2.0 backport train lands. Do not treat anything here as
shipped behaviour.

## Why

Someone browsing the repo should be able to **see** the themes and the
components before adopting the library. Today the README documents the
component inventory and the theme list as text only. Two visual artefacts are
planned, both generated by a script we run when preparing a release, with the
PNG outputs committed so `README.md` can embed them.

## Tier 1 — theme showcase banner (README header image)

Run when preparing a new release: render a grid of several **basic
components** as row items — e.g.

- button (`AppButton`, a few variants: primary / secondary / ghost / danger)
- text input (`AppInput` with a value)
- pills (`AppChip` / `AppBadge`)
- toggle (`AppToggle` on)
- icon row (`AppIcon`)

under every included theme as **columns** (13 themes: dark, light, late-night,
thermal, neon-cyberpunk, grunge, granite, classic, high-contrast, bubblegum,
matrix, shining-gold, pure-platinum).

- Output: one PNG. If 13 columns make it too wide for the README, split into
  **two images** (e.g. 7 + 6 themes) and embed both side by side.
- Location: `docs/assets/theme-banner.png` (or `docs/assets/theme-banner-1.png`
  + `-2.png`), referenced at the top of `README.md` near the intro.
- Each theme column is rendered by setting `data-theme` on the test
  document's root — same mechanism the playground's ThemeBar uses. Include the
  theme *label* in the column header so the image is self-describing.

## Tier 2 — per-component catalogue (README preview grids)

A superset of Tier 1: render **every component in the inventory** (primitives,
inputs, overlays, navigation, data display, layout, charts, calendar, board)
showing real output under **three themes**:

1. light (`[data-theme="light"]`)
2. dark (the `:root` default)
3. thermal (`[data-theme="thermal"]`)

- Output: one grid image per component family (or per component for the large
  ones), all three themes as columns or a 3-up strip; embedded in the README's
  component inventory section so a user can preview before choosing.
- The existing `playground/` is the natural harness: its per-family sections
  already exercise each component with realistic data. Plan is to give the
  playground a **print route** that renders a fixed grid (no chrome, no
  interactivity) and screenshot it per theme, rather than hand-building a
  second harness that rots.
- Charts/calendar/board need deterministic seed data (they already have it:
  `seedBoard()`, `seedEvents()`) so the images are reproducible.

## Implementation guidance (when it is picked up)

- **Renderer:** headless browser screenshots — Playwright (or Puppeteer) is
  the expected tool; the library itself must not gain a runtime dependency for
  this. Screenshots are a dev-time/CI-only concern.
- **Script shape:** `scripts/render-release-banner.ts` (Tier 1) and a
  catalogue renderer (Tier 2), runnable via `npm run render:release`
  (devDependency only). Vite `preview` or a static build serves the harness;
  the script drives the headless browser, sets `data-theme`, screenshots each
  grid, and writes the committed PNGs.
- **Reproducibility:** fixed viewport, `prefers-reduced-motion` on (durations
  are 0ms), deterministic seeds — a diff of the output PNGs across releases
  should show *only* real visual changes.
- **Freshness:** the images must be regenerated whenever a component or theme
  changes; the release-preparation checklist should include this step (along
  side README inventory updates).

## Out of scope / open questions

- Whether Tier 2 ships as README images per family or a single long gallery
  image — decide when implementing (README size vs. usefulness of per-family
  anchors).
- Tier 1 column count: single vs. two images — the split rule of thumb is
  "fit at 800px README width without squint".
- CI enforcement (e.g. a job that re-runs the renderer and fails on diff) is
  desirable but not required for the first cut.
